# GPU 驱动可见性试验场

项目名：GPUVisibilityLab  
版本：1.0 | 更新日期：2026-09-22  
定位：面向游戏引擎开发与实时图形岗位的 C++ / D3D12 学习型实验项目  
状态：A1 已在学习记录中完成验收；A2 进行中；本文后续功能均为计划，不代表已经实现。

## 1. 一句话目标

在同一个可重复生成的实例场景中，对比“不剔除、CPU 单线程剔除、CPU 多线程剔除、GPU 剔除与间接绘制”，用正确性检查和 CPU / GPU 分项计时解释：**什么时候值得把可见性判断交给 GPU，收益来自哪里，成本又在哪里。**

这不是一个完整游戏引擎，也不是只展示大量方块的性能演示。最终作品应同时具备可交互演示、清晰源码、可复现实验和能讲明白的结论。

本项目第一版中的“可见性”指**视锥内的候选可见性**。视锥内、但被其他物体挡住的对象仍会被保留；遮挡剔除属于后续可选扩展，不能把两者混称。

## 3. 差异化与岗位对应

**差异化来自实验设计和解释能力，不来自堆砌 API 名词。**

| 展示点 | 要回答的问题 | 能体现的能力 |
|---|---|---|
| 四条可切换路径 | 相同输入下，它们做的是不是同一件事？ | 控制变量、接口设计、调试能力 |
| 可见对象 ID 对照 | 画面看起来相同，是否真的没有漏掉对象？ | 几何算法、CPU/GPU 数据一致性 |
| GPU 自己生成绘制参数 | GPU 结果是否还要先读回 CPU 才能画？ | Compute、数据压缩、间接绘制、资源同步 |
| CPU 线程数扫描 | 多线程从什么规模开始有收益？ | 任务拆分、生命周期、竞争与调度成本 |
| 完整成本分析 | 剔除省下的绘制时间是否覆盖了它自身的成本？ | 性能测量、瓶颈分析、工程判断 |

面向引擎岗位，重点讲清对象所有权、帧资源复用、CPU 工作线程协作、构建和回归验证。面向图形岗位，重点讲清视锥数学、GPU 数据流、间接绘制、屏障和时间测量。两种讲法使用同一份真实工程，不需要为此再写两套项目。

允许并鼓励出现这样的结论：小场景 CPU 单线程更快，某些负载 CPU 多线程收益有限，可见比例很高时 GPU 剔除反而增加成本。**项目不以“GPU 必须获胜”为验收标准。**

## 5. 对照实验模式

| 模式 | 可见性判断 | 绘制输入 | 核心用途 |
|---|---|---|---|
| M0：不剔除 | 不做视锥测试 | 所有实例，直接实例化绘制 | 测出剔除前的总成本 |
| M1：CPU 单线程 | 主线程测试所有包围球 | CPU 生成可见 ID 并上传，直接实例化绘制 | 参考结果与简单实现基线 |
| M2：CPU 多线程 | 工作线程分块测试 | 合并各线程结果，上传并直接实例化绘制 | 观察并行收益与调度、合并成本 |
| M3：GPU 驱动 | Compute Shader 测试包围球 | GPU 生成可见 ID 和实例数，通过 `ExecuteIndirect` 绘制 | 验证不经 CPU 读回的绘制闭环 |

**公平性要求：** M0/M1/M2 也采用实例化批量绘制，不能故意让 CPU 路径每个对象单独提交一次 Draw，以制造 GPU 方案的夸张收益。四条路径的场景、网格复杂度、分辨率、图形 Shader 和画质设置保持一致；剔除与提交路径的差异单独记录。

增加一个小型诊断对照：CPU 预先填好固定间接参数，不运行剔除，比较直接实例化绘制与间接绘制。它用于隔离间接提交的成本，不作为第五个复杂功能分支。

第一版只需生成一条 `DRAW_INDEXED` 类型的间接命令，GPU 决定其中的 `InstanceCount`。命令条数保持为 1，实例数为 0 时不产生实例绘制；这里不需要先实现“可变命令数量”或多网格分桶。D3D12 的命令签名描述参数布局，`ExecuteIndirect` 按该布局读取参数缓冲。[微软间接绘制说明](https://learn.microsoft.com/en-us/windows/win32/direct3d12/indirect-drawing)

## 6. 核心数据流

```text
固定种子场景 + 对象变换 + 世界空间包围球 + 当前相机
    |
    +-- M0：全部对象 ID
    +-- M1：CPU 单线程测试 -> 可见 ID -> 上传
    +-- M2：CPU 分块测试 -> 局部结果合并 -> 可见 ID -> 上传
    +-- M3：GPU 测试 -> 可见 ID 压缩 -> 生成间接绘制参数
    |
统一实例数据与图形 Shader -> 绘制 -> Present

验证路径：结果拷贝到 Readback -> 等对应 Fence 完成 -> CPU 比较
计时路径：CPU 计时 + GPU Timestamp -> 延迟收集 -> CSV / 报告
```

M3 的最小实现顺序是：重置本帧计数器，运行剔除 Dispatch，通过 GPU 原子操作为可见 ID 分配输出位置，再由一个小型 Dispatch 把最终数量写入间接参数。只允许 GPU 在当帧绘制链路中消费这些结果，不在每帧读回数量后由 CPU 决定 Draw。

顶点着色器通过实例索引读取可见 ID，再访问对应对象的变换数据。可见 ID、计数器与间接参数都要有明确的容量、布局和帧归属；容量至少覆盖允许的最大实例数，并测试无越界、无重复 ID。

先用单个 Direct Queue 串联 Compute 与 Draw，减少跨队列问题。根据实际读写依赖设置 UAV 屏障和状态转换，间接参数执行前进入适当的 `INDIRECT_ARGUMENT` 状态。**CPU 提交顺序不等于所有资源访问都已正确同步；资源屏障与 Fence 也不是相互替代的东西。** [微软资源屏障说明](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12)

A2 的“每帧等待 GPU”只作为入门模型。进入正式性能对照前，建立按 Fence 保护的帧资源，避免 CPU 提前覆盖 GPU 尚在使用的分配器、上传数据和输出缓冲。正常性能路径不靠每帧全量等待或即时 Readback 保证正确。

## 7. 多线程学习路线

多线程服务于 CPU 对照实验，不从通用 Job System 开始，也不与 GPU 编程同时引入所有复杂度。

1. 理解线程入口、捕获变量的生命周期、`join`、数据竞争，先写固定数据集上的离线小测试。
2. 让多个线程读取不可变的对象和相机快照，每个线程只写自己的结果缓冲。
3. 按对象索引连续分块，任务完成后统一合并；避免多个线程在循环内争抢一个共享 `vector`。
4. 使用标准 C++ 同步设施建立简单的常驻工作线程，明确启动、等待任务、完成通知和退出条件，不每帧创建销毁线程。
5. 分别测量剔除、调度等待和结果合并；扫描 1、2、4、8 个工作线程，更多线程只作为附加实验，不预设最大线程数一定最快。

验收不只看“程序没有崩溃”：同一输入的可见 ID 集合必须与 M1 一致；工作线程结束前输入对象必须存活；正常退出能回收所有线程；性能报告包含并行开销，而不是只记录最短的工作线程耗时。

## 9. 正确性验收

### 统一数学与数据约定

明确记录矩阵的存储和乘法约定、坐标系、投影方式、深度范围与 HLSL 上传约定；不能直接把旧 OpenGL 代码的近裁剪面提取公式当作 D3D12 公式使用。第一版先采用普通深度方案，不同时引入反向 Z。

包围球平面测试采用一个明确约定：平面法线朝内且归一化时，若 `dot(n, center) + d < -radius - epsilon`，则球位于该平面外侧。只要被任一平面排除，就可以剔除；否则保守地保留。包围球与六平面测试可能保留实际没有可见几何的对象，这是保守策略允许的结果，不承诺精确几何可见性。CPU 与 GPU 使用相同输入和容差策略，容差不能用来掩盖稳定出现的错误。

### 最小测试集

- 球完全在视锥内、完全在视锥外，分别越过六个平面。
- 球与平面相交或相切、球心在视锥外但球体与视锥相交、相机位于球内。
- 0 个对象、全部不可见、全部候选可见、达到当前最大容量。
- 连续帧从全可见切换到全不可见，确认计数器和间接实例数没有沿用上一帧。
- 多个随机种子、固定相机轨迹、不同工作线程数，重复运行结果稳定。

几何函数先通过有人工预期结果的测试，再把 M1 用作 M2/M3 的对照。不能只因为 CPU 与 GPU 同时算错、结果相同，就认定数学正确。

验证 GPU 结果时，Readback 必须对应明确的场景快照、相机和帧编号，并在相应 Fence 完成后读取。原子压缩的输出顺序不保证固定，**应比较 ID 集合，不只比较数量，也不要求输出顺序相同**；验证用排序、去重等操作不进入正式性能路径。

通过标准：不误剔可见对象，测试结果符合已定义的保守包围球规则，ID 无重复/越界，计数与有效 ID 数量一致，且没有未解决的调试层警告或错误。画面截图是证据之一，不是唯一判据。

## 10. 性能实验规范

### 先测什么

| 指标 | 用途与限制 |
|---|---|
| CPU 剔除时间 | 对 M1/M2 比较实际算法成本；M2 还要记录调度与合并 |
| CPU 上传、录制与提交时间 | 不把数据准备成本隐藏在“剔除之外” |
| CPU 帧处理与等待时间 | 区分真正的 CPU 工作、Fence 等待和 Present 阻塞 |
| GPU 剔除与参数生成时间 | 测量 M3 新增的 GPU 工作 |
| GPU 绘制时间与完整工作区间 | 判断节省的绘制是否抵消 Compute 和同步开销 |
| 总对象数、候选可见数、可见比例 | 解释同一算法为何在不同场景表现不同 |
| 帧时间中位数与 P95 | 展示典型表现和波动，平均 FPS 只作辅助 |

GPU 时间使用 Timestamp Query 和执行队列的计时频率换算，不用 CPU 包围 `ExecuteCommandLists` 的耗时冒充 GPU 执行时间。查询结果延迟读取；CPU/GPU 会重叠执行，不能把二者耗时简单相加称为帧时间。[微软 GPU 计时说明](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing)

### 可复现实验条件

1. 对象规模先测试 1,000、10,000、100,000 三档，结合实际运行能力调整；不是必须跑到百万对象。
2. 设计低、中、高候选可见比例场景，并记录实际测得的比例；全部使用相同种子与相机配置进行四模式对照。
3. 固定分辨率、网格复杂度、图形 Shader、呈现设置和相机轨迹。正式报告记录配置，不把不同画质的结果并排当作算法收益。
4. 将正确性和性能运行分开：正确性运行开启调试层；性能运行使用 Release、关闭调试层及验证回读，明确记录其他诊断开关。
5. 性能运行排除 VSync/帧率上限造成的瓶颈，并记录呈现设置；用 GPU 工作区间解释结果，不只看窗口 FPS。
6. 初始协议为预热至少 120 帧、采样至少 600 帧、每个条件独立运行至少 3 次。低负载时延长采样，保留各次结果，不只挑最好一次。
7. 每次保存代码版本、硬件与驱动版本、构建配置、对象数量、种子、相机轨迹、模式、工作线程数、分辨率和开关。先定义 CSV 字段和单位，再写统计脚本。

测试矩阵可以分批扩大：先在一个固定场景证明四模式可比较，再增加对象规模、可见比例和线程数；不要第一天就跑大量尚未验证的性能数据。

## 11. 最终交付与完成定义

- **可运行演示：** 支持选择四种模式、固定场景、移动相机、暂停与重放轨迹；显示模式、对象数与基本计时信息。
- **正确性材料：** 数学单元测试、CPU/GPU 可见集合对比结果、边界案例和调试层检查记录。
- **性能材料：** 原始 CSV、统计方式、至少三类负载的对照图表，以及成本与收益的解释。
- **工程材料：** 干净构建说明、依赖来源与版本、必要的目录说明、失败时能定位问题的日志。
- **展示材料：** 一段约 2～3 分钟的演示视频和简短技术说明，能讲清目标、方案、验证、结果与限制。

v1.0 完成必须同时满足：四模式可运行且公平对照、结果验证通过、完整 GPU 数据流可解释、性能实验可复现、文档与源码状态一致。漂亮画面或单个高 FPS 数字不能替代这些条件。

简历中的数量、耗时和加速比只填写实测值，并写明对比基线与测试条件。在得到数据前，不预写“提升若干倍”或“百万物体实时渲染”等结论。
